# Self-Hosting Setup

Betterlytics is designed to be simple to self-host while remaining privacy-focused and lightweight.
This guide walks you through deploying Betterlytics on your own infrastructure using Docker.

All self-hosting files and configuration live in the [betterlytics-selfhost](https://github.com/betterlytics/betterlytics-selfhost) repository.

## Requirements

- **Docker Engine 25** or newer with **Docker Compose v2.24** or newer. Check with `docker version` and `docker compose version`
- A **hostname** the instance is reached at, pointed at your server or your reverse proxy (not needed to try it locally)
- Ports **80** and **443** reachable from the internet (standalone mode), or a reverse proxy you already run

## Quick Start

<Steps>

### Clone the Repository

```bash
git clone https://github.com/betterlytics/betterlytics-selfhost.git
cd betterlytics-selfhost
```

### Run the Setup Script

The interactive setup script generates your `.env` file and any necessary Docker Compose overrides:

```bash
./setup.sh
```

It asks for a deployment mode and your domain:

- [**Standalone**](#standalone): the container provisions HTTPS certificates itself. Pick this when nothing else listens on ports 80 and 443.
- [**Basic**](#behind-a-reverse-proxy): plain HTTP on a port of your choice, for use behind your own reverse proxy.
- [**Try locally**](#try-locally): plain HTTP on `localhost`, to try Betterlytics on your own computer.

<Callout type="info">
Prefer to configure manually? Copy `.env.example` to `.env` and fill in the values yourself. The [configuration reference](#configuration-reference) below lists every option.
</Callout>

### Start the Containers

```bash
docker compose up -d --wait
```

The first start runs database migrations before the app comes up, so give it a minute or two. If the instance doesn't come up, `docker compose logs` shows why, see [Troubleshooting](#troubleshooting). Run the same command after any change to `.env` to apply it.

Then open your domain in a browser and create your account.

<Callout type="info">
The first account created on a new instance becomes its admin. The instance is reachable as soon as it starts, so create your account right after `docker compose up -d --wait` returns. Everyone else joins by invitation, see [Users and Email](#users-and-email).
</Callout>

### Install the Tracking Script

Once logged in, follow the in-app integration guide to add the tracking script to your website. The snippet it generates already points at your instance. It looks like this:

```html
<script
  async
  src="https://analytics.example.com/analytics.js"
  data-site-id="your-site-id"
  data-server-url="https://analytics.example.com/event"
></script>
```

<Callout type="warning">
The snippets elsewhere in these docs are written for Betterlytics Cloud: they load `analytics.js` from `betterlytics.io` and send events there. When copying one, change the script origin and add `data-server-url`, or the npm package's `scriptUrl` and `serverUrl` options, as shown in [Tracking Scripts](#tracking-scripts).
</Callout>

The [Integration Overview](/integration) covers what the script can do.

</Steps>

## Deployment Modes

The instance can be the public endpoint and manage its own certificate, or sit behind a proxy you already run. `setup.sh` asks which. When configuring by hand, the `TLS` variable in `.env` is the switch, see [Domain and HTTPS](#domain-and-https).

### Standalone

In standalone mode the container faces the internet directly. It gets a certificate from Let's Encrypt and renews it automatically. Ports 80 and 443 must both be open: Let's Encrypt verifies your domain over port 80, and HTTPS traffic arrives on 443.

`setup.sh` configures this for you. If you are setting up manually, set the following in `.env`:

```bash
PUBLIC_URL=https://analytics.example.com
TLS=auto

# Reachable from the internet on port 80, where Let's Encrypt verifies the domain
BIND_ADDRESS=0.0.0.0
HTTP_PORT=80
```

and create a `docker-compose.override.yml` that exposes port 443:

```yaml
services:
  betterlytics-selfhost:
    ports:
      - "0.0.0.0:443:443"
```

`HTTP_PORT` must be `80`, otherwise Let's Encrypt can't verify the domain, and `PUBLIC_URL` must be an `https://` address with a public hostname and no port. `SSL_EMAIL` and `ACME_CA` are optional; see [Domain and HTTPS](#domain-and-https).

### Behind a Reverse Proxy

This is the **Basic** mode in `setup.sh`. If you already have a reverse proxy (Caddy, Nginx, Traefik, etc.), set `TLS=off` in `.env` and bind to a custom port so the instance itself never terminates TLS:

```bash
PUBLIC_URL=https://analytics.example.com
TLS=off
BIND_ADDRESS=127.0.0.1
HTTP_PORT=5566
```

`setup.sh` in Basic mode binds to `127.0.0.1`, so the port is only reachable from the same machine. When the proxy runs elsewhere, set `BIND_ADDRESS` to the interface it connects through, or `0.0.0.0` for all interfaces, and firewall the port accordingly.

Your proxy must serve Betterlytics over HTTPS at exactly `PUBLIC_URL`, because logins only work from that address. If the proxy listens on a port other than 443, include it: `PUBLIC_URL=https://analytics.example.com:8443`. It must also pass the `Host` header through unchanged and set `X-Forwarded-Proto` and `X-Forwarded-For`. Example configurations for a proxy on the same machine, forwarding to the default port `5566`:

<Tabs items={['Caddy', 'Nginx', 'Traefik']}>
  <Tabs.Tab>
    ```
    analytics.example.com {
        reverse_proxy 127.0.0.1:5566
    }
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    ```nginx
    server {
        listen 443 ssl;
        server_name analytics.example.com;

        ssl_certificate     /etc/letsencrypt/live/analytics.example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/analytics.example.com/privkey.pem;

        client_max_body_size 6m;

        location / {
            proxy_pass http://127.0.0.1:5566;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    Add a router and service in your Traefik dynamic configuration:

    ```yaml
    http:
      routers:
        betterlytics:
          rule: "Host(`analytics.example.com`)"
          entryPoints:
            - websecure
          tls:
            certResolver: letsencrypt
          service: betterlytics

      services:
        betterlytics:
          loadBalancer:
            servers:
              - url: "http://127.0.0.1:5566"
    ```

    If you use Docker labels instead of file-based configuration, add these to the Betterlytics service in your `docker-compose.override.yml`. Traefik talks to the container directly, so the port is the container's port 80, not `HTTP_PORT`:

    ```yaml
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.betterlytics.rule=Host(`analytics.example.com`)"
      - "traefik.http.routers.betterlytics.entrypoints=websecure"
      - "traefik.http.routers.betterlytics.tls.certresolver=letsencrypt"
      - "traefik.http.services.betterlytics.loadbalancer.server.port=80"
    ```
  </Tabs.Tab>
</Tabs>

Proxies on the same host or a private network are trusted automatically. If your proxy connects from a public address, add it to the `TRUSTED_PROXIES` variable in `.env` (see [Network](#network)), otherwise every visitor is recorded with the proxy's IP. To check, compare `request.remote_ip` and `request.client_ip` in `docker compose logs betterlytics-selfhost`.

Sign-in rate limits need one more setting behind your own proxy. Until the `AUTH_TRUSTED_PROXIES` variable in `.env` is set, all sign-in attempts share one limit, so a few failed logins block sign-in for everyone for about 10 seconds. Set it to the exact address your proxy connects from, which is the `request.remote_ip` value in those logs (usually the Docker bridge gateway, for example `172.18.0.1`). List that single address rather than a whole private range, because a client inside a trusted range can choose the address it is counted under. The gateway address can change when the Docker network is recreated, so check it again if sign-in limits become shared. If you set `TRUSTED_PROXIES`, add the same entries here.

### Plain HTTP or IP Access

To serve Betterlytics without TLS, at an IP address or an internal hostname on a network you trust, configure `.env` by hand. `setup.sh` doesn't offer this, because its Basic mode expects a hostname your proxy serves over HTTPS. Start from the `.env` that `setup.sh` wrote in Basic mode, or from a copy of `.env.example` with `SECRET_BASE` set, then set:

```bash
PUBLIC_URL=http://192.168.1.10:5566
BIND_ADDRESS=0.0.0.0
```

`PUBLIC_URL` must be the exact address browsers use, including the port unless it is 80. That port is `HTTP_PORT`, `5566` by default. Apply it with `docker compose up -d --wait`. To try Betterlytics on your own computer, use [Try Locally](#try-locally) instead.

<Callout type="warning">
Over plain HTTP, passwords and sessions cross the network unencrypted. Only do this on a network you trust, and firewall the port: `BIND_ADDRESS=0.0.0.0` listens on every interface.
</Callout>

### Try Locally

The third `setup.sh` mode runs the instance on `http://localhost:5566` with no domain and no TLS. Use it to try Betterlytics on your own computer, not for a real deployment.

## Tracking Scripts

The in-app integration guide fills in your instance's address. The snippets elsewhere in these docs are written for Betterlytics Cloud, so when you copy one, change two things:

- Load `analytics.js` from your instance instead of `betterlytics.io`
- Send events to your instance's `/event` endpoint. Without this, the tracker sends them to Betterlytics Cloud

<Tabs items={['Script tag', 'npm package']}>
  <Tabs.Tab>
    ```html
    <script
      async
      src="https://analytics.example.com/analytics.js"
      data-site-id="your-site-id"
      data-server-url="https://analytics.example.com/event"
    ></script>
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    ```js
    import betterlytics from "@betterlytics/tracker";

    betterlytics.init("your-site-id", {
      scriptUrl: "https://analytics.example.com/analytics.js",
      serverUrl: "https://analytics.example.com/event",
    });
    ```
  </Tabs.Tab>
</Tabs>

Every other attribute and option in the [integration guides](/integration) works unchanged next to these. The [WordPress plugin](/wordpress/configuration#self-hosted-instances) has its own settings for the same two addresses.

The session replay and Web Vitals scripts load from the same origin as `analytics.js`. If you serve `analytics.js` from somewhere else, for example a CDN in front of your instance, set `data-scripts-base-url` on the script tag to the origin they should load from.

### Content Security Policy

If your website sends a `Content-Security-Policy` header, allow your instance's origin for loading the scripts and for sending data:

```text
script-src 'self' https://analytics.example.com;
connect-src 'self' https://analytics.example.com;
```

`script-src` covers `analytics.js` and the session replay and Web Vitals scripts. `connect-src` covers everything the tracker sends. If you set `data-scripts-base-url`, add that origin to `script-src` too.

## Geolocation

Betterlytics can resolve visitor IP addresses to countries, regions and cities using [MaxMind's](https://www.maxmind.com/) GeoLite2 database. This is optional. Without it, the dashboard shows no visitor locations.

<Steps>

### Create a MaxMind Account

Sign up for a free account at [maxmind.com/en/geolite2/signup](https://www.maxmind.com/en/geolite2/signup).

### Generate a License Key

Once logged in, navigate to **Account > Manage License Keys** and click **Generate New License Key**.

![MaxMind license key page](/images/self-hosting/maxmind-license-key.webp)

After completing the flow, you'll be shown your license key. Copy it (you won't be able to see it again).

### Configure Your Environment

Add the following to your `.env` file:

```bash
ENABLE_GEOLOCATION=true
# "country" (default) or "full", which adds regions and cities
GEOLOCATION_MODE=full
MAXMIND_ACCOUNT_ID=your_account_id
MAXMIND_LICENSE_KEY=your_license_key
```

Your Account ID is displayed at the top of the MaxMind account portal. The [Geolocation reference](#geolocation-1) lists all options.

### Restart

```bash
docker compose up -d --wait
```

The GeoLite2 database downloads on first start and updates automatically. If the instance doesn't come back up, see [Troubleshooting](#troubleshooting).

</Steps>

Location data is only added to events recorded after geolocation is turned on, and regions and cities only after `GEOLOCATION_MODE=full` is set. Neither can be backfilled, because IP addresses are never stored.

## Session Replay

Session Replay is enabled by default and stores recordings in ClickHouse alongside your analytics data. Nothing is recorded until you turn on replay in the tracking script for a website. See the [Session Replay integration guide](/integration/session-replay) for the script attributes, sampling, and masking options.

Recordings are kept for 60 days by default. Set the `REPLAY_RETENTION_DAYS` variable in `.env` to keep them longer, or to `-1` to keep them indefinitely; this is independent of analytics retention. Set `SESSION_REPLAYS_ENABLED=false` to remove the feature from the instance. Apply either change with `docker compose up -d --wait`.

### Storing Recordings in Your Own S3

Recordings can go to S3-compatible object storage instead of ClickHouse. Add the following to your `.env`:

```bash
S3_ENABLED=true
S3_BUCKET=betterlytics-replays
S3_REGION=eu-central-1
S3_ENDPOINT=https://s3.example.com
S3_ACCESS_KEY_ID=your_access_key
S3_SECRET_ACCESS_KEY=your_secret_key
# Required for most non-AWS providers (MinIO, Garage, etc.)
S3_FORCE_PATH_STYLE=true
```

The endpoint only needs to be reachable from the containers, never from visitors' browsers.

<Callout type="warning">
`REPLAY_RETENTION_DAYS` only applies to recordings stored in ClickHouse. With S3, expire the `site/` prefix with a lifecycle rule on your bucket.
</Callout>

## Uptime Monitoring and Status Pages

The main differences from Cloud are how alerts are delivered and where the page is served. Monitors and their Slack, Discord, Teams, and webhook alerts work out of the box, and can reach services on your private network, see [Monitoring Internal Services](#monitoring-internal-services). Email alerts need [email sending configured](#email), and Pushover alerts need the `PUSHOVER_APP_TOKEN` variable in `.env` set to your own Pushover application token.

A published status page is served by your instance at:

```
https://analytics.example.com/status/{your-slug}
```

Everything described in the [Public Status Pages guide](/dashboard/status-pages) applies. Removing the Betterlytics branding and serving a page on your own domain are available on every self-hosted instance.

## Monitoring Internal Services

Uptime monitors and the generic webhook integration can reach services on your private network out of the box. A self-hosted instance allows private (RFC 1918 and IPv6 unique local) and CGNAT (`100.64.0.0/10`, used by Tailscale) addresses on any port, and generic webhooks may use plain `http://` URLs. This lets you monitor services like `http://grafana.home.lan:3000` and send alerts to n8n, ntfy or Home Assistant on your LAN.

Link-local addresses (`169.254.0.0/16` and `fe80::/10`) are always blocked. They include the cloud metadata endpoint `169.254.169.254`, which exposes credentials on most cloud servers.

Loopback addresses (`127.0.0.0/8` and `::1`, including `localhost`) are always blocked too. Inside the Betterlytics container they only reach Betterlytics' own internal services, never your server. To monitor a service on the same server, use the server's LAN IP address or `host.docker.internal`.

To turn this off, for example on an instance shared with people you do not fully trust, add the following to your `.env` and apply it with `docker compose up -d --wait`:

```bash
ALLOW_PRIVATE_TARGETS=false
```

With `ALLOW_PRIVATE_TARGETS=false`, monitors behave like on Betterlytics Cloud: they only reach public addresses on ports 80 and 443, and webhooks need a public `https://` URL.

Monitors can only target URLs on their dashboard's domain or its subdomains. To monitor internal hosts, create a dashboard for your internal domain (for example `home.lan`, which covers `grafana.home.lan`) or for the host's IP address.

## Custom Status Page Domains

A status page can be served from its own domain, for example `status.acme.com`, instead of `/status/{your-slug}` on your instance. Enter the domain in the status page's **Settings** tab and publish the page; then set up DNS and TLS for the deployment mode you run.

**Standalone (`TLS=auto`):** add a CNAME record pointing the domain at your instance's hostname, the host of its `PUBLIC_URL`. The certificate is issued automatically the first time the domain is visited after the page is published. No `.env` change and no restart are needed. Certificates are only issued for domains that a published status page claims.

| Type  | Name (host) | Value (target)          |
|-------|-------------|-------------------------|
| CNAME | `status`    | `analytics.example.com` |

**Behind a reverse proxy (`TLS=off`):** your proxy terminates TLS for the extra hostname and forwards it to the same port with the `Host` header unchanged. Betterlytics picks the status page from `Host`. Every custom domain needs its own entry in the proxy, next to the one for your instance:

<Tabs items={['Caddy', 'Nginx']}>
  <Tabs.Tab>
    ```md
    analytics.example.com {
        reverse_proxy 127.0.0.1:5566
    }

    # Custom status page domains, all forwarded with Host unchanged
    status.acme.com, status.other.com {
        reverse_proxy 127.0.0.1:5566
    }
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    ```nginx
    server {
        listen 443 ssl;
        server_name status.acme.com;

        ssl_certificate     /etc/letsencrypt/live/status.acme.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/status.acme.com/privkey.pem;

        location / {
            proxy_pass http://127.0.0.1:5566;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
    ```
  </Tabs.Tab>
</Tabs>

**Proxy on another machine:** replace `127.0.0.1` with the instance's private address and point the domain's DNS at that proxy.

**No proxy (registrar forwarding):** forward `status.acme.com` to `https://analytics.example.com/status/{your-slug}` with a plain redirect (not "masked" forwarding) from a forwarder that supports HTTPS. Leave the **Custom domain** field empty, so the page keeps its instance URL as its canonical address.

See the [Custom Status Page Domain guide](/integration/custom-status-page-domain) for the in-app steps and DNS troubleshooting.

## Users and Email

### Adding Users

The first account is created on the sign-up page of a new instance. After that, sign-up is closed and new people join by invitation only.

To invite someone, open a dashboard, go to **Settings > Members**, enter their email address, pick a role, and click **Invite**. Owners and admins of the dashboard can invite. With [email set up](#setting-up-email), the invitation arrives by email. Without it, nothing is sent: click **Copy invite link** next to the invitation and pass the link on yourself. The invited person opens the link and creates their account with the email address you invited. Invite links expire after 7 days.

An invitation gives access to one dashboard. To give someone access to several, invite them from each one.

Accounts on a self-hosted instance are never asked to verify their email address.

### What Needs Email

Email is off by default. Everything else works without it, but these features need it:

- **Password reset:** the **Forgot your password?** link on the sign-in page only appears when email is set up
- **Invitation emails:** invite links work without email, see above
- **[Email reports](/dashboard/email-reports)**
- **Email alerts for [uptime monitors](/dashboard/monitoring):** Slack, Discord, Teams, Pushover, and webhook alerts work without email
- **Security notices** about password changes and two-factor authentication

Emails are sent by the instance's background jobs, which are on by default. With `BACKGROUND_JOBS_ENABLED=false`, no email is sent at all.

### Lost Passwords and Two-Factor Authentication

Without email, a forgotten password cannot be reset. To recover an account, [set up email](#setting-up-email), apply it with `docker compose up -d --wait`, and use **Forgot your password?** on the sign-in page.

Someone who loses their authenticator app signs in with one of the backup codes shown when they turned on two-factor authentication. Each code works once, and new ones can be generated under **User Settings > Account**. This works without email.

### Setting Up Email

Set `ENABLE_EMAILS=true`, a sender address in `SMTP_FROM`, and one provider in `.env`:

<Tabs items={['SMTP', 'MailerSend']}>
  <Tabs.Tab>
    ```bash
    ENABLE_EMAILS=true
    SMTP_FROM=analytics@example.com
    SMTP_HOST=smtp.example.com
    SMTP_PORT=587
    SMTP_USER=your_smtp_username
    SMTP_PASSWORD=your_smtp_password
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    ```bash
    ENABLE_EMAILS=true
    SMTP_FROM=analytics@example.com
    MAILER_SEND_API_TOKEN=your_api_token
    ```
  </Tabs.Tab>
</Tabs>

`SMTP_FROM` is required with either provider, MailerSend included, and the instance does not start without it. Use an address on a domain your email provider has verified, optionally with a display name: `SMTP_FROM="Acme Analytics <analytics@example.com>"`. Apply the change with `docker compose up -d --wait`. The [Email reference](#email) lists every option.

## Configuration Reference

All options are read from `.env` in the repository root. Database passwords, auth secrets, and internal tokens are derived from `SECRET_BASE`, so that is the only secret you need to set. After editing `.env`, run `docker compose up -d --wait`.

### Domain and HTTPS

| Variable | Default | Behavior |
|----------|---------|----------|
| `PUBLIC_URL` | | The full address browsers use: scheme, host and, if non-standard, the port, for example `https://analytics.example.com` or `https://analytics.example.com:8443`. No path. Logins, links, and the tracking snippet all use exactly this address. Use `http://` only when browsers reach the instance over plain HTTP, as in [Try Locally](#try-locally) and [Plain HTTP or IP Access](#plain-http-or-ip-access) |
| `TLS` | `off` | `auto` enables built-in Let's Encrypt certificates (standalone mode) and needs an `https://` `PUBLIC_URL` with a public hostname and no port. `off` serves plain HTTP, for use behind your own proxy, locally, or on a trusted network |
| `SSL_EMAIL` | unset | Optional contact address registered with your Let's Encrypt account |
| `ACME_CA` | Let's Encrypt production | Optional ACME directory URL. Use `https://acme-staging-v02.api.letsencrypt.org/directory` while testing to avoid rate limits |

### Network

`BIND_ADDRESS` and `HTTP_PORT` are advanced settings: the defaults fit a reverse proxy on the same machine, and `setup.sh` sets them for standalone mode.

| Variable | Default | Behavior |
|----------|---------|----------|
| `BIND_ADDRESS` | `127.0.0.1` | Interface the exposed ports listen on. `0.0.0.0` for standalone mode or a proxy on another machine |
| `HTTP_PORT` | `5566` | Host port mapped to the container's port 80. Must be `80` with `TLS=auto` |
| `TRUSTED_PROXIES` | | Extra proxy IPs or CIDRs whose forwarded headers are trusted, for proxies on public addresses |
| `AUTH_TRUSTED_PROXIES` | | Only behind your own proxy: the IPs or CIDRs it connects from, so sign-in rate limits apply per visitor instead of being shared. See [Behind a Reverse Proxy](#behind-a-reverse-proxy) |

### Secrets

| Variable | Default | Behavior |
|----------|---------|----------|
| `SECRET_BASE` | | Single secret all passwords and auth keys derive from. Use at least 32 random characters, for example the output of `openssl rand -hex 32`; `setup.sh` generates one. The instance logs a warning at startup when it is empty, `CHANGEME`, or shorter than 32 characters. Keep it once the instance has started: the databases were created with passwords derived from it |

### Email

| Variable | Default | Behavior |
|----------|---------|----------|
| `ENABLE_EMAILS` | `false` | Enables outgoing email: password resets, invitations, reports, alerts, and security notices. Needs `SMTP_FROM` and one provider below |
| `SMTP_FROM` | | Sender for all outgoing mail, MailerSend and SMTP alike. Required when `ENABLE_EMAILS=true`; the instance does not start without it. Use an address on a domain your email provider has verified, optionally with a display name: `"Acme Analytics <analytics@example.com>"` |
| `MAILER_SEND_API_TOKEN` | | MailerSend API token. When set, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER` and `SMTP_PASSWORD` are not needed, but `SMTP_FROM` still is. If both are set, MailerSend is used |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` | | SMTP server for other providers. `SMTP_PORT` defaults to `587` |

### Geolocation

| Variable | Default | Behavior |
|----------|---------|----------|
| `ENABLE_GEOLOCATION` | `false` | Master switch. When disabled, no geo data is collected |
| `MAXMIND_ACCOUNT_ID` | | MaxMind account ID |
| `MAXMIND_LICENSE_KEY` | | MaxMind license key |
| `GEOLOCATION_MODE` | `country` | `country`: country-level data only. `full` adds subdivision + city drill-down |
| `ENABLE_ASN_LOOKUP` | `false` | Looks up each visitor's network (ASN) to improve bot detection. Downloads MaxMind's GeoLite2-ASN database with `MAXMIND_ACCOUNT_ID` and `MAXMIND_LICENSE_KEY`; the instance refuses to start when that download fails |

### Session Replay

| Variable | Default | Behavior |
|----------|---------|----------|
| `SESSION_REPLAYS_ENABLED` | `true` | Set to `false` to disable the feature |
| `REPLAY_RETENTION_DAYS` | `60` | Days to keep recordings, `-1` for indefinitely. ClickHouse storage only |
| `REPLAY_STORAGE` | derived | `clickhouse` or `s3`. Resolves to `s3` when `S3_ENABLED=true` |
| `S3_ENABLED`, `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE` | | Your own S3-compatible storage, see [Storing Recordings in Your Own S3](#storing-recordings-in-your-own-s3) |
| `S3_SSE_ENABLED` | `false` | Set to `true` to request server-side encryption (SSE-S3, AES256) for recordings uploaded to your bucket |

### Other

| Variable | Default | Behavior |
|----------|---------|----------|
| `BACKGROUND_JOBS_ENABLED` | `true` | Runs the background worker, which sends all outgoing email and runs the data-retention cleanup. `false` stops both |
| `PUSHOVER_APP_TOKEN` | | Pushover application token for uptime alerts via Pushover |
| `ALLOW_PRIVATE_TARGETS` | `true` | Uptime monitors and webhooks may reach private and LAN addresses on any port, and webhooks may use `http://`. Loopback and link-local addresses stay blocked. `false` limits them to public addresses as on Cloud, see [Monitoring Internal Services](#monitoring-internal-services) |
| `PUBLIC_ENABLE_FAVICON_FETCHING` | `true` | Site icons in the dashboard are fetched server-side from DuckDuckGo (`icons.duckduckgo.com`), which learns each domain whose icon is shown. `false` stops these requests, and a generic globe icon is shown instead |
| `LOG_LEVEL` | `info` | Backend log level: `error`, `warn`, `info`, `debug` or `trace` |

## Updating

<Callout type="warning">
Coming from v1.3.5 or earlier? Read **Upgrading from v1.3.5 or earlier** below before you pull: it needs a backup, free disk space and `.env` changes. An instance that still has the old `.env` stops at start.
</Callout>

Each release bumps the image version pinned in `docker-compose.yml`, so updating the `betterlytics-selfhost` repository is what upgrades your instance:

```bash
git pull
docker compose up -d --wait
```

Compose pulls the new image on its own. Read the release notes first for version-specific steps such as backups or disk space.

<Callout type="info">
Major updates may run one-time database migrations on first boot. Do not interrupt the container while they run.
</Callout>

<details>
<summary>Upgrading from v1.3.5 or earlier</summary>

Releases after v1.3.5 run one-time ClickHouse migrations that rewrite the events table, replace nginx and certbot with Caddy, and move two-factor authentication to a new system. Before upgrading:

- Ensure free disk space of at least 2 to 3 times the size of your ClickHouse data volume. The events table is rewritten twice, and the space is reclaimed at the end.
- Expect a long first boot on large installations.
- Back up the `betterlytics_selfhost_clickhouse_data` and `betterlytics_selfhost_postgres_data` volumes first.
- If `ENABLE_EMAILS=true`, set `SMTP_FROM` to an address on a domain your email provider has verified. Earlier versions sent as `info@betterlytics.io` when it was unset, which providers reject; the instance now refuses to start without it.
- In standalone mode, keep port 80 reachable from the internet. Caddy requests new certificates on first boot and validates them over port 80.
- If `git pull` reports local changes in `base/proxy` or `base/.env.base`, save a copy, discard them with `git checkout -- base`, and pull again. The nginx templates are replaced by a Caddy configuration that ships inside the image, so move proxy changes to [your own reverse proxy](#behind-a-reverse-proxy), or mount a Caddy configuration directory of your own over `/etc/caddy` in `docker-compose.override.yml`. If you changed `DATA_RETENTION_DAYS` there, add the same line to `.env`, for example `DATA_RETENTION_DAYS=-1`, before running `docker compose up`. The first boot carries the value in `.env` over to your dashboards, see below.
- Replace the address variables in `.env`. `DOMAIN`, `HTTP_SCHEME`, `FORCE_HTTP_SCHEME` and `HTTPS_PORT` are replaced by `PUBLIC_URL` and `TLS`; `HTTP_PORT` and `BIND_ADDRESS` keep their meaning:

  | Old `.env` | New `.env` |
  |------------|------------|
  | `HTTP_SCHEME=https` | `PUBLIC_URL=https://<DOMAIN>` and `TLS=auto` |
  | `HTTP_SCHEME=http` | `PUBLIC_URL=https://<DOMAIN>` and `TLS=off` |
  | `HTTP_SCHEME=http` with `FORCE_HTTP_SCHEME=http` | `PUBLIC_URL=http://<DOMAIN>` and `TLS=off` |
  | `HTTPS_PORT` | Remove it. If your `docker-compose.override.yml` uses `${HTTPS_PORT}`, write `443` there first |

  An instance whose `.env` still has only the old names stops at start, and `docker compose logs betterlytics-init` prints the two lines to add.

After the first boot:

- **Two-factor authentication is reset.** Existing authenticator enrollments cannot be carried over, so 2FA is turned off for every account that had it. Users sign in with their password and turn it on again under **User Settings > Account**. Affected users are notified by email only when [email sending](#email) is configured and background jobs are enabled.
- **Retention is set per dashboard.** A dashboard's owner or admin sets its retention under **Settings > Data**, where self-hosted instances also offer **Keep forever**. On the first boot every dashboard keeps at least the retention your instance enforced before: 1 year, or `DATA_RETENTION_DAYS` from `.env` when set. `-1` makes every dashboard **Keep forever**, and a value above `365` becomes the next longer period (2, 3 or 5 years, or **Keep forever** above 5 years). Dashboards with a longer period stay as they are. A shorter period picked there on v1.3.5 never took effect, so it is raised too. This happens once. After that `DATA_RETENTION_DAYS` has no effect and the container log warns while it is set, so remove it from `.env`.
- **The old certificate volumes are left behind.** Certificates now live in the `betterlytics_selfhost_caddy_data` volume. Once HTTPS works, find the old volumes with `docker volume ls`, their names end in `letsencrypt_certs` and `certbot_www`, and remove them with `docker volume rm`.

<Callout type="warning">
A cleanup job deletes data older than each dashboard's retention every Saturday at 02:00 UTC. Before then, check every dashboard under **Settings > Data** and choose **Keep forever** or a longer period wherever you want to keep more. If you upgraded without carrying a longer `DATA_RETENTION_DAYS` into `.env`, your dashboards were set to 1 year; adding it afterwards changes nothing, so set the longer period on each dashboard before the cleanup runs. To hold the cleanup until every dashboard owner has checked, set `BACKGROUND_JOBS_ENABLED=false`; this also pauses outgoing email.
</Callout>

</details>

You can follow new releases on [GitHub](https://github.com/betterlytics/betterlytics/releases).

## Troubleshooting

### Containers won't start

- Verify Docker and Docker Compose are installed and running
- Check that required ports (80/443 in standalone mode) are not in use
- Review container logs: `docker compose logs`
- `TLS=auto requires HTTP_PORT=80`: set `HTTP_PORT=80` in `.env` and map port 443 as shown under [Standalone](#standalone), or switch to `TLS=off` behind your own proxy
- `DOMAIN, HTTP_SCHEME and FORCE_HTTP_SCHEME are no longer read`: replace them with `PUBLIC_URL` and `TLS`, see "Upgrading from v1.3.5 or earlier" under [Updating](#updating)
- `Configuration/image version mismatch`: the log shows the repository and image versions. Run `git pull`, then `docker compose up -d --wait` again. If only `betterlytics-selfhost` keeps restarting, an override changes its image; `docker compose logs betterlytics-selfhost` shows the same message
- `Cannot find module '/init'` in the `betterlytics-init` log: an override pins an image from before this release. Remove the image override
- `Geolocation is enabled but no GeoIP database could be obtained`: check `MAXMIND_ACCOUNT_ID` and `MAXMIND_LICENSE_KEY`, or set `ENABLE_GEOLOCATION=false`
- `ENABLE_EMAILS=true requires SMTP_FROM on self-hosted instances`: set `SMTP_FROM` in `.env` to your sender address (MailerSend needs it too), or set `ENABLE_EMAILS=false`, then `docker compose up -d --wait` again

### HTTPS certificate not provisioning

- Ensure your domain's DNS A record points to your server
- Ports 80 and 443 must both be reachable from the internet, and `HTTP_PORT` must be `80`. Certificates are validated over port 80
- Check the container logs for ACME errors: `docker compose logs`
- Testing repeatedly? Set `ACME_CA` to the Let's Encrypt staging directory to avoid rate limits

### Can't sign in

- **"This page is open at …, which doesn't match the address…":** open the instance at its `PUBLIC_URL`, or fix `PUBLIC_URL` in `.env` and run `docker compose up -d --wait`.
- The logs confirm it: `docker compose logs betterlytics-selfhost | grep "Invalid origin"`.
- `setup.sh` Basic mode no longer accepts an IP address; see [Plain HTTP or IP Access](#plain-http-or-ip-access).
- **"Too many attempts":** wait about 10 seconds. Sign-in allows 3 attempts per 10 seconds per IP.
- Sign-in, invite links, and tracking snippets all use `PUBLIC_URL`, so other addresses, such as the server's IP or a second hostname pointing at it, don't work. In standalone mode the browser shows a certificate or connection error for them instead of the sign-in page.
- Behind your own proxy, check that it passes the `Host` header unchanged and sets `X-Forwarded-Proto`.

### Custom status page domain shows a certificate error

- Confirm the status page is **published**. Certificates are only issued for domains a published page claims
- Confirm the CNAME record points at your instance's hostname, the host of its `PUBLIC_URL`
- `docker compose logs betterlytics-selfhost | grep permission` shows the hostname and why the certificate was refused: `404` not published or unknown, `403` reserved name, `429` lookup ceiling
- Automatic certificates for custom domains require standalone mode. Behind your own proxy, the proxy must hold the certificate for the domain

### No analytics data appearing

- Verify the tracking script is installed on your website with the correct site ID
- Check that `data-server-url` points at your instance, not at `betterlytics.io`
- Check that the `/event` endpoint is reachable from the browser
- Review backend logs: `docker compose logs`
