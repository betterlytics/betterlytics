# Error Tracking

Betterlytics captures client-side errors from your site and sends them to your dashboard. Identical errors are automatically grouped so you can track unique issues over time.

## Quick start

### Using the script tag

Add `data-track-errors="true"` to your analytics script to start capturing errors and `data-track-console-errors="true"` to also capture `console.error()` calls:

```html
<script
  async
  src="https://betterlytics.io/analytics.js"
  data-site-id="your-siteid"
  data-track-errors="true"
  data-track-console-errors="true"
>
</script>
```

<Callout type="info">
Self-hosting? Load `analytics.js` from your instance and send events to it, with the script tag and the npm package alike. [Tracking Scripts](/installation/self-hosting#tracking-scripts) in the Self-Hosting guide shows the two changes.
</Callout>

### Configuration reference

| Attribute | Type | Default | Description |
| --- | --- | --- | --- |
| `data-track-errors` | boolean | `false` | Enables error tracking. |
| `data-track-console-errors` | boolean | `false` | Also captures `console.error()` calls. Requires `data-track-errors="true"`. |
| `data-track-failed-requests` | boolean | `false` | Also captures failed `fetch` and `XMLHttpRequest` requests. Requires `data-track-errors="true"`. See [Failed requests](#failed-requests). |
| `data-dynamic-api-urls` | string | none | Comma-separated patterns that group request URLs with ids, in the same syntax as [`data-dynamic-urls`](/integration/dynamic-urls). See [Grouping request URLs](#grouping-request-urls). |
| `data-replay-on-error` | boolean | `false` | Captures a replay when an error occurs, even for sessions not sampled for regular recording. Requires `data-replay="true"` and consent. See [Error-triggered replay](#error-triggered-replay). |

### Using the npm package

Error tracking is disabled by default. Enable it with `trackErrors`:

```ts
import betterlytics from '@betterlytics/tracker';

betterlytics.init('your-site-id', {
  trackErrors: true, // true | false (default)
});
```

To also capture `console.error()` calls:

```ts
betterlytics.init('your-site-id', {
  trackErrors: true,
  trackConsoleErrors: true, // true | false (default)
});
```

See the package docs for the full API and options: [@betterlytics/tracker on npm](https://www.npmjs.com/package/@betterlytics/tracker).

## What gets captured

Betterlytics captures four types of errors:

- **JavaScript errors**: runtime errors like `TypeError`, `ReferenceError`, etc. that are not caught by your code.
- **Failed promises**: promises that reject without being handled.
- **Console errors** (optional): `console.error()` calls. Enable with `data-track-console-errors="true"`.
- **Failed requests** (optional): `fetch` and `XMLHttpRequest` requests that get a 5xx response, fail on the network or time out. Enable with `data-track-failed-requests="true"`. See [Failed requests](#failed-requests).

## Failed requests

With `data-track-failed-requests="true"`, Betterlytics records failed requests made by your page:

```html
<script
  async
  src="https://betterlytics.io/analytics.js"
  data-site-id="your-siteid"
  data-track-errors="true"
  data-track-failed-requests="true"
>
</script>
```

- **5xx responses** from any domain appear as `HTTPError`, for example `GET https://example.com/api/orders 503`.
- **Network failures** appear as `NetworkError` and **timeouts** as `TimeoutError`, but only for requests to your site's own domain and its subdomains (a leading `www.` is ignored). Requests to other domains often fail because of ad blockers, so they are skipped.
- 1xx to 4xx responses, requests your page cancels, opaque `no-cors` responses and Betterlytics' own requests are never recorded.
- Only the method, the URL without its query string and fragment, the status code, the duration and the failure type are sent. Query strings, headers and request or response bodies are never sent.

Failures with the same method, URL and status (or failure type) are grouped into one error. Your page's requests behave exactly as before.

An unhandled network failure in your own code can also show up separately as an uncaught `TypeError: Failed to fetch`.

### Grouping request URLs

Request URLs with ids, like `/api/orders/123` and `/api/orders/456`, form separate error groups until you add a pattern for them. Use `data-dynamic-api-urls` with the same wildcards as [Dynamic URLs](/integration/dynamic-urls), matched on the request path:

```html
<script
  async
  src="https://betterlytics.io/analytics.js"
  data-site-id="your-siteid"
  data-track-errors="true"
  data-track-failed-requests="true"
  data-dynamic-urls="/users/*"
  data-dynamic-api-urls="/api/orders/*,/api/users/*/invoices/*"
>
</script>
```

With this configuration, a failed `GET /api/orders/123` is recorded as `GET https://example.com/api/orders/* 503`.

Requests to your page's own host try your `data-dynamic-urls` patterns first and then `data-dynamic-api-urls`. Requests to other hosts only use `data-dynamic-api-urls`.

## Errors and Session Replay

When error tracking is combined with [Session Replay](/integration/session-replay), errors are automatically linked to replay recordings. You can jump from any error in the dashboard directly to the session replay to see what the user experienced.

If a session is already being recorded, errors are linked to it automatically with no extra configuration needed.

### Error-triggered replay

For sessions that are not being recorded, you can enable `data-replay-on-error` to capture a replay anyway. Betterlytics records in the background and only uploads when an error occurs, giving you around **1-2 minutes of context** before the error. Sessions without errors are never uploaded.

```html
<script
  async
  src="https://betterlytics.io/analytics.js"
  data-site-id="your-siteid"
  data-track-errors="true"
  data-replay="true"
  data-consent-replay="true"
  data-replay-on-error="true"
>
</script>
```

Or with the npm package:

```ts
betterlytics.init('your-site-id', {
  enableSessionReplay: true,
  trackErrors: true,
  replayOnError: true, // true | false (default)
});
```

## Scripts hosted on a CDN or different domain

If your JavaScript is served from a different domain than your page, browsers block error details from cross-origin scripts. You will only see `"Script error."` with no stack trace.

To fix this, add `crossorigin="anonymous"` to your script tags and make sure your CDN is configured to allow it:

```html
<script src="https://cdn.example.com/app.js" crossorigin="anonymous"></script>
```

## Privacy

Error messages may occasionally contain sensitive data, such as URLs with user IDs. Make sure your application does not include personal data in error messages.

## Best practices

- Enable alongside [Session Replay](/integration/session-replay) to get full context for every error.
- Use `data-track-console-errors` if your dependencies log errors rather than throw them.
- Triage errors regularly using the Resolved and Ignored statuses.
- Check for new error groups after each deploy.

## Troubleshooting

- **No errors appearing**: Verify `data-track-errors="true"` is set on your analytics script.
- **Missing stack traces**: If you only see `"Script error."`, see [Scripts hosted on a CDN or different domain](#scripts-hosted-on-a-cdn-or-different-domain).
- **Console errors not captured**: Set `data-track-console-errors="true"` alongside `data-track-errors="true"`.
- **Failed requests not captured**: Set `data-track-failed-requests="true"` alongside `data-track-errors="true"`. Network failures and timeouts are only recorded for your own domain and its subdomains.
